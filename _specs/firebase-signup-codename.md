# Spec for Firebase Signup with Generated Codename

branch: claude/feature/firebase-signup-codename
figma_component (if used): n/a

# Summary

Wire the existing signup form (`/signup`, rendered by `AuthForm` with `mode="signup"`) to Firebase Authentication using the shared exports from `lib/firebase.ts`. On successful signup, a random three-part codename is generated by picking one word from each of 3 distinct word sets and jamming them together in PascalCase. This codename is set as the user's auth `displayName`, and a document is created for the user in the Firestore `users` collection storing their codename and id — never their email. Only the Firebase Web SDK is used (no Admin SDK).

# Functional requirements

- Submitting the signup form creates a new Firebase Auth user from the entered email and password, using the `auth` instance exported from `lib/firebase.ts`.
- On success, generate a codename: pick one word at random from each of 3 distinct word sets (each set internally unique; exact word lists/themes are an implementation choice) and concatenate them in PascalCase with no separators.
- Update the newly created user's auth profile so their `displayName` equals the generated codename.
- Create a document in the Firestore `users` collection (via the `db` export), keyed by the user's uid, containing exactly:
  - `codename` — the generated codename (same value as `displayName`)
  - `id` — the user's uid
  - Explicitly NOT the user's email (or password).
- While the signup request is in flight, show a pending state on the submit button and prevent double submission.
- Surface Firebase auth errors (e.g. email already in use, weak password, invalid email) as a friendly inline message near the form; do not navigate on failure.
- On full success, redirect the user into the authenticated area (see Open Questions for destination).
- Reading auth state elsewhere in the app continues to go through `useUser()` from `UserProvider`; this feature only performs the signup mutation.
- The login mode of `AuthForm` remains unchanged (out of scope).

# Possible Edge Cases

- Email already registered → inline error shown; no `users` document created.
- Weak password or malformed email → Firebase validation error surfaced inline.
- Partial failure: auth user is created but the `displayName` update or the Firestore write fails → user exists without a complete profile; behaviour must be decided (see Open Questions).
- Network offline or Firestore security rules deny the write.
- Codename collisions are possible since generation is random with no uniqueness check.
- User navigates away or closes the tab mid-signup.
- Rapid double click on the submit button before the request resolves.

# Acceptance Criteria

- Given a fresh email and valid password, submitting the signup form results in: a new Firebase Auth user whose `displayName` is a PascalCase three-word codename, and a `users/{uid}` document containing exactly `codename` and `id`, with no email field anywhere in the document.
- Every generated codename consists of exactly three words, one drawn from each of the three sets, joined in PascalCase.
- On failure (e.g. email already in use), an understandable error message is displayed and the user stays on `/signup`.
- The submit button is disabled/pending while the signup request is in flight.
- After successful signup, the user lands on the agreed authenticated destination.

# Open Questions

- What are the three word sets (themes and contents)? Adjectives / colours / animals — see `lib/codename.ts`
- Should codename uniqueness across users be enforced (e.g. re-roll on collision)? No — random generation only, collisions allowed
- What is the post-signup redirect target — `/heists` or elsewhere? /heists
- If account creation succeeds but the profile/doc write fails, should we retry, show an error, or attempt cleanup? show an error
- Should the codename generator live somewhere reusable for future features? Yes — `lib/codename.ts` exports the word sets and generator

# Testing Guidelines

Create a test file(s) in the ./tests folder for the new feature, and create meaningful tests for the following cases, without going too heavy:

- Successful signup calls Firebase Auth with the entered email/password, updates the profile displayName to a PascalCase codename, and writes the `users` doc with only `codename` and `id`.
- Codename generation shape: exactly three PascalCase words joined together (control randomness via mocks).
- Rejected signup (e.g. email already in use) renders an error message and does not navigate.
- Pending/disabled submit state while signup is in flight.
- Mock `firebase/auth` and `firebase/firestore` per AGENTS.md notes (`onAuthStateChanged` callback at args index `[1]`; mock must return the unsubscribe function).
